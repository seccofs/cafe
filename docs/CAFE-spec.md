## 1. Overview

CAFE is a chunk-based image format (inspired by PNG), using **ZSTD** as the block compression algorithm, with space reserved in the format for future algorithms. The encoder applies automatic fallback to raw data when compression is not beneficial. Supports alpha channel by default, indexed palette with real sub-byte index packing, a broad set of predictive filters per block (tile), interlaced display, streaming decoding, and application metadata (EXIF, JSON, ICC, XMP). Supports HDR at the format level (`Sample format` float/half in `IHDR` + `cHDR` chunk, section 7), with an extension path for a complete HDR color pipeline without breaking compatibility.

This version (v1.1) consolidates the design after the Rust reference implementation, including full support for advanced predictive filters (filters 0-15, with the new TR-Directional `14` and adaptive Weighted `15` added in v1.1), Shannon Entropy heuristic for automatic filter selection, structured metadata (EXIF, JSON, ICC, XMP), optimized indexed palette, and security hardening against malformed/malicious inputs (section 12).

## 2. File Signature

Every `.cafe` file starts with 9 fixed bytes:

```
0x89 0x43 0x41 0x46 0x45 0x0D 0x0A 0x1A 0x0A
```

This corresponds to the sequence `\x89CAFE\r\n\x1a\n` (pure ASCII, no accent).

Function of each part (same logic as PNG):

| Bytes | Function |
|---|---|
| `0x89` | High byte — detects transmission that truncates bit 7 (7-bit text mode) |
| `0x43 0x41 0x46 0x45` (`CAFE`) | Readable mark of the format |
| `0x0D 0x0A` (`\r\n`) | Detects corruption from CRLF↔LF conversion |
| `0x1A` | Ctrl-Z — interrupts file type on Windows/DOS |
| `0x0A` (`\n`) | Detects corruption from LF↔CRLF conversion (inverse of `\r\n`) |

## 3. Chunk Structure

Every chunk follows this layout:

| Field | Size | Description |
|---|---|---|
| Length | 4 bytes (uint32 BE) | Size of `Data` field |
| Type | 4 bytes (ASCII) | Chunk identifier (e.g., `IHDR`) |
| Flag | 1 byte | Codec used in this chunk — see enum in section 3.2 |
| Data | N bytes | Chunk content (raw or compressed according to Flag) |
| CRC32 | 4 bytes | CRC32 over `Type + Flag + Data` |

### 3.1 Type Naming Convention (critical vs. ancillary)

The `Type` field must contain exactly 4 alphabetic ASCII characters (`A`–`Z`, `a`–`z`). No other byte is allowed in this field — this is what guarantees that the convention below (based on uppercase/lowercase) is well-defined for every chunk, including those that a future implementation might add.

Following the PNG convention:
- **1st letter uppercase** → critical chunk (decoder must understand or reject the file)
- **1st letter lowercase** → ancillary chunk (decoder can safely ignore if not recognized, or silently discard if malformed — see section 12.4)

### 3.2 `Flag` Field Enum and Compression Fallback Rule

CAFE uses **ZSTD** as the block compression algorithm. The `Flag` field reserves space for future algorithms without requiring changes to the format structure if that becomes necessary — but no algorithm beyond ZSTD is defined in this version.

The encoder tests compression and writes the result that produces the smallest `Data`, including the option to write raw if compression does not compress better than the original.

**`Flag` Values:**

| Value | Meaning |
|---|---|
| `0x00` | Raw data (no compression) |
| `0x01` | Compressed with ZSTD |
| `0x02`–`0xFF` | Reserved for future compression algorithms |

**Encoding logic (applicable to any compressible chunk):**

```
candidates = [
    (0x00, original_chunk_data),
    (0x01, zstd.compress(original_chunk_data, level)),
]

Flag, Data = smallest(candidates, key=size_in_bytes)
```

That is, the `0x00` (raw) candidate always competes — if compression does not result in a `Data` smaller than the original size, the block is written without compression.

**Interoperability note:** the `Data` field of a chunk with `Flag = 0x01` is a valid ZSTD frame, but the spec **does not require** that this frame declare the size of decompressed content in its header (the `content size` parameter, optional in ZSTD format). Different libraries/languages have different standards as to whether to include this field automatically. A CAFE decoder should use a decompression API that **does not depend on** this field being present (e.g., streaming read, instead of an "all at once" API that requires size in advance) — otherwise, files generated by encoders that omit this field will fail in decompression without real reason related to the CAFE format itself.

**Security note:** every decoder must enforce a configurable upper limit on the output size of any decompression (see section 12.2, protection against "decompression bomb"). This is not optional — it is part of the safe decoding contract of the format.

## 4. Defined Chunks

### 4.1 `IHDR` (critical, always first, always uncompressed)

| Field | Size | Description |
|---|---|---|
| Width | 4 bytes | uint32 BE |
| Height | 4 bytes | uint32 BE |
| Bit depth | 1 byte | Bits per channel (or per index, in palettes): 1, 2, 4, 8, 10, 12, 16, 32 — see restrictions by color type in sections 4.1.1 and 4.1.2 |
| Sample format | 1 byte | `0`=uint, `1`=float, `2`=half-float (fp16) |
| Color type | 1 byte | `0`=gray, `2`=RGB, `3`=indexed (requires PLTE), `4`=gray+alpha, `6`=RGBA (**default**) |
| Compression method | 1 byte | Bitmask of codecs used in the file — `bit0`=ZSTD, remaining bits reserved (0) for future algorithms |
| Filter method | 1 byte | `0`=none, `1`=byte-shuffle (implemented, section 4.3.2), `2`=predictive (code per block, see complete enum in section 4.3.1) |
| Interlace method | 1 byte | `0`=none, `1`=Adam7, `2`=even/odd |

> Alpha channel by default: `Color type = 6` (RGBA) is the recommended value. If the source image has no alpha, the encoder fills with `0xFF` (opaque).

> **`Filter method = 1` (byte-shuffle, implemented since v1.1):** preprocessing technique for multi-byte samples (bytes per pixel ∈ `{2, 4, 8, 16}`), designed especially for float/HDR data: reorders bytes by position within the sample — all least significant bytes of all pixels first, then most significant — which typically compresses float data much better than natural interleaved order (correlation between bytes of the same position survives compression better). The exact layout, restrictions, and pipeline order are in section 4.3.2. An old decoder finding `Filter method = 1` must **explicitly reject the file** (it is an `IHDR` field, therefore critical — same logic as section 5.1 for `Interlace method`), never treat it silently as equivalent to `0` (no filter).

> **Compression method (bitmask):** the encoder sets `bit0` if at least one chunk in the file uses `Flag = 0x01` (ZSTD). Additional bits are reserved for future compression algorithms. This allows the decoder to verify, immediately after reading `IHDR`, if it supports all codecs present in the file — and reject the file immediately if it does not support some, instead of failing in the middle of decompressing an `IDAT`.

**Total: 14 bytes of payload in IHDR.**

#### 4.1.1 Rules for `Bit depth = 1` (pure bilevel/bitmap)

Supports strictly black-and-white images (1 bit per pixel, no intermediate tones — e.g., fax, technical drawing, binarized scans).

- **Allowed color types**: `0` (no alpha) and `4` (with alpha). When `4`, the alpha channel is also stored as 1 bit per pixel (binary mask: opaque/transparent, no middle ground).
- **Sample format**: must be `0` (uint). `bit depth = 1` with `sample format = 1` or `2` (float) is invalid — decoder must reject the file.
- **Packing**: pixels are packed 8 per byte, MSB first (most significant bit = leftmost pixel), same as PNG. If the block/tile width is not a multiple of 8, the remaining bits of the last byte of each line are filled with `0` and ignored in decoding.
- **Filter method**: `1` (byte-shuffle, section 4.3.2) does not apply to `bit depth = 1`, since there are no multi-byte samples to reorder. The predictive filters from section 4.3.1 (`Filter method = 2`) remain valid, operating on already-packed bytes — not on individual bits.
- **Interlace**: compatible with `Adam7` and even/odd, but bit packing is recalculated per pass (each pass has its own pixel count per line, hence its own padding scheme at line end).
- **Compression fallback**: applies normally (section 3.2) to the bit-packed buffer — ZSTD typically compresses this type of data well, given the high redundancy of binary patterns.

#### 4.1.2 Rules for `Color type = 3` (indexed) and `PLTE` Chunk

Supports indexed color palettes (images with few distinct colors — icons, pixel art, graphics, simple screenshots), dramatically reducing size before even ZSTD compression.

**`PLTE` — critical chunk, mandatory when `Color type = 3`, must appear before first `IDAT`:**

| Field | Size | Description |
|---|---|---|
| Entry format | 1 byte | `0` = RGB (3 bytes/entry), `1` = RGBA (4 bytes/entry) |
| Entries | N × (3 or 4 bytes) | Palette colors, in order of their indices (0, 1, 2, ...) |

- With `entry format = 1` (RGBA), each palette entry already carries its own alpha channel — no separate `tRNS` chunk is needed as in PNG.
- Follows the standard compression fallback rule (section 3.2), although palettes are typically small enough that the gain is marginal.

**Additional rules when `Color type = 3`:**

- **Bit depth** represents bits per **pixel index** (not per color channel): valid values are `1, 2, 4, 8`. Maximum palette entries = `2^bit_depth` (e.g., bit depth 8 → up to 256 colors).
- **Index packing (implemented):** when `bit depth` is `1`, `2` or `4`, multiple indices are packed per byte, **MSB first**, with zero padding at line end if width is not a multiple of byte capacity — same logic as section 4.1.1. Bytes per line = `ceil(width × bit_depth / 8)`. The reference implementation automatically chooses the smallest `bit_depth` that accommodates the palette color count (e.g., palette with up to 2 colors → `bit_depth = 1`; up to 16 colors → `bit_depth = 4`).
- **Sample format** must be `0` (uint). Index as float is invalid.
- **Filter method**: the predictive filters from section 4.3.1 operate on already-packed bytes (not on indices/individual bits), valid for any `bit depth`. Byte-shuffle (section 4.3.2) **does not** apply to palettes: indices have 1 byte/pixel (`bytes per pixel = 1`, outside the required `{2, 4, 8, 16}` set), and an encoder must not write `Filter method = 1` with `Color type = 3`.
- If the decoder finds `Color type = 3` without a preceding `PLTE` chunk, it must reject the file.

#### 4.1.3 Pixel Byte Layout

General rules for how bytes of a pixel/line/sample are organized, applicable to all color types:

- **Channel order within pixel**: `Color type = 6` (RGBA) stores channels in order **R, G, B, A**. `Color type = 2` (RGB) stores **R, G, B**. `Color type = 4` (gray+alpha) stores **Gray, Alpha**. `Color type = 0` (gray) stores only the gray channel. `Color type = 3` (indexed) stores the pixel index (no direct color channels — color comes from `PLTE`, section 4.1.2).
- **Line order**: line `0` is the **top** line of the image/tile; lines proceed top-to-bottom, same as PNG convention.
- **Endianness of multi-byte samples**: any sample with more than 8 bits (`bit depth = 10, 12, 16, 32`) is stored in **big-endian**, consistent with all other multi-byte fields in the format (`Width`, `Height`, `Length`, `CRC32`). This also applies to float fields in `cHDR` chunk (section 4.4) — all in IEEE 754 big-endian.
- **Packing of `bit depth = 10` and `12`**: each sample occupies a **16-bit integer container** (2 bytes, big-endian), with unused most significant bits filled with `0`. That is, a 12-bit sample occupies the 12 least significant bits of a `uint16`, and the 4 most significant bits are always `0`. This prioritizes implementation simplicity (same read logic as `bit depth = 16`) over maximum bit density — the "wasted" space before compression is, in practice, absorbed by ZSTD, so the actual cost after compression is small.

### 4.2 `iDIM` (ancillary, optional, defines partitioning for streaming)

| Field | Size | Description |
|---|---|---|
| Tile width | 2 bytes | Tile width in pixels |
| Tile height | 2 bytes | Tile height in pixels |
| Tiles X | 2 bytes | Number of tiles horizontally |
| Tiles Y | 2 bytes | Number of tiles vertically |
| Scan order | 1 byte | `0`=row by row, `1`=Z-order (Morton) |

If absent, the decoder assumes a single `IDAT` chunk covering the entire image (no tiling), or row-strips of size arbitrarily defined by the encoder (see section 4.3 — row-strip partitioning does not require `iDIM`; it is only needed for real 2D tiling or to signal streaming order).

**Order of `IDAT` appearance:** when the encoder uses real 2D tiling (not just row-strips), `IDAT` chunks appear in the file in the same order defined by `Scan order`, without need for an explicit index per chunk:

- `Scan order = 0` (row by row): tiles in row-major order — left→right within each tile row, then top→bottom (first all tiles of row `tile_y = 0`, then `tile_y = 1`, and so on).
- `Scan order = 1` (Z-order/Morton): tiles ordered by Morton code (bits of `tile_x` and `tile_y` interleaved) of their coordinates `(tile_x, tile_y)` in the grid — same logic used for progressive preview by spatial region (section 6).

The N-th `IDAT` chunk in the file (counting only `IDAT` chunks, 0-indexed) corresponds to the N-th position in this enumeration order.

**Edge tiles (width/height not multiples of tile):** no padding. When `width` is not a multiple of `Tile width`, tiles in the last column (`tile_x = Tiles X - 1`) have actual width `width − (Tiles X − 1) × Tile width` (less than `Tile width`). The same applies to the last tile row (`tile_y = Tiles Y - 1`) relative to `height` and `Tile height`. The decoder calculates these reduced dimensions from `Width`/`Height` (IHDR) and `Tile width`/`Tile height`/`Tiles X`/`Tiles Y` (iDIM) — no additional field per tile is needed.

### 4.3 `IDAT` (critical, one or more per file)

Contains the pixels (or palette indices) of a block/tile of the image. Each `IDAT` is **independent** — can be compressed or not (fallback rule from section 3.2), and decoded as soon as it arrives (streaming).

**Order of operations in encoding an `IDAT`:**

```
raw pixels of block/tile (or packed palette indices, section 4.1.2)
    → (if Filter method = 2) apply predictive filter per block (section 4.3.1)
    → (if Filter method = 1) apply byte-shuffle per block/tile (section 4.3.2)
    → (if interlace ≠ 0) prefix pass_number
    → apply compression fallback rule (section 3.2), optionally with
      ZSTD dictionary (section 4.9, zDIC) if present in file
```

**Payload before compression** (when interlace ≠ 0):

```
[pass_number: 1 byte][block lines, already filtered if Filter method = 2]
```

When interlace = 0, the payload is directly the block/tile lines (already filtered if applicable), with no additional header beyond what section 4.3.1 describes.

Interlacing (Adam7 and even/odd, section 5) applies to both direct RGBA images and indexed palette images — in the latter case, the reference implementation converts indices to RGBA before interlacing, since the 7 Adam7 passes (of different resolutions) do not combine directly with variable-sized palettes per pass.

#### 4.3.1 Predictive Filter (`Filter method = 2`)

Reduces data entropy **before** compression, predicting the value of each pixel byte (or index) from already-known neighbors and storing only the residual (difference). It is a preprocessing technique, not compression — it works together with ZSTD from section 3.2, not instead of it.

**Choice per block (entire tile):** a single filter is chosen for the entire block (the set of lines that make up an `IDAT`); all lines of the block share the same predictor. The first 5 are the classic PNG ones; the rest are CAFE additions:

| Code | Filter | Prediction used (per sample byte) |
|---|---|---|
| `0` | None | None — original byte kept |
| `1` | Sub | Byte of left pixel (`L`), same line |
| `2` | Up | Byte of pixel above (`U`), same column, previous line |
| `3` | Average | Average (`L`, `U`), rounded down |
| `4` | Paeth | Left, above, or top-left diagonal (`UL`) — chosen by Paeth predictor |
| `5` | MED (Median Edge Detector) | `L`, `U`, and `UL` — see formula below |
| `6` | Gradient (Plane) | `L + U − UL`, no clamping — see formula below |
| `7` | Simple Median | Simple median of 3 neighbors (`L`, `U`, `UL`), without MED edge logic |
| `8` | 2nd Order | `(2×L − LL + 2×U − UU) / 2`, with clamping to `[0, 255]` — see formula below |
| `9` | 4-way Directional (Horizontal) | `(3×L + U) / 4` — favors horizontal continuity |
| `10` | 4-way Directional (Vertical) | `(L + 3×U) / 4` — favors vertical continuity |
| `11` | 4-way Directional (Diagonal `\`) | `(L + U + 2×UL) / 4` |
| `12` | 4-way Directional (Diagonal `/`) | `(2×L + 2×U + UL) / 5` |
| `13` | Context-Based | Detects local orientation by gradient and dynamically chooses between Sub, Up, or Average — see formula below |
| `14` | TR-Directional | Bilinear average of 4 neighbors (`L`, `UL`, `U`, `TR`) — WebP "Predictor 10" (added in v1.1) — see formula below |
| `15` | Weighted (adaptive) | Adaptive weighted average of `L`, `U`, `UL`, `TR` — inspired by JPEG-XL weighted predictor (added in v1.1) — see formula below |

**MED Formula** (same predictor used by JPEG-LS and FFV1):

```
if UL >= max(U, L):
    prediction = min(U, L)
else if UL <= min(U, L):
    prediction = max(U, L)
else:
    prediction = U + L - UL
```

**Gradient/Plane Formula** (one of 7 classic JPEG Lossless modes):

```
prediction = (U + L − UL) mod 256
```

**Context-Based Formula:**

```
dh = |L − UL|   (horizontal difference)
dv = |U − UL|   (vertical difference)

if dh > dv:  prediction = L   (vertical edge detected → Sub filter)
else if dv > dh:  prediction = U   (horizontal edge detected → Up filter)
else:  prediction = (L + U) / 2   (homogeneous region → Average)
```

**TR-Directional Formula** (filter `14`, WebP "Predictor 10"; added in v1.1):

It is the only filter in the format that consumes the top-right neighbor (`TR`): the byte of the pixel to the right, in the previous line (`x + bpp`). Absent at the right edge of the tile, `TR` is treated as zero (same zero convention as other missing neighbors).

```
avg2(p, q) = (p + q) >> 1          (truncated average, no overflow — 16-bit arithmetic)
prediction   = avg2( avg2(L, UL), avg2(U, TR) )
```

The bilinear combination gives twice the weight to diagonal information that Average (`3`) ignores, making it useful for smooth curvature and diagonal gradients `/` that no `L`/`U`/`UL` predictor captures.

**Weighted Formula** (filter `15`, inspired by JPEG-XL weighted predictor; added in v1.1):

Maintains a weight state `w[L], w[U], w[UL], w[TR]` — integers in `[0, 64]`, initially `8` each — reset per block and persistent across block lines. For each byte, in scan order (left→right, top→bottom):

```
Σw     = w[L] + w[U] + w[UL] + w[TR]
prediction = clamp( ( w[L]·L + w[U]·U + w[UL]·UL + w[TR]·TR + Σw/2 ) / Σw , 0, 255 )
```

After knowing the actual value `v` (original byte in encoder; `residual + prediction` in decoder — both sides get the same `v`), the state is updated, rewarding the neighbor that was closest:

```
e_i = |v − neighbor_i|   (for each of 4 neighbors)
average = (e_L + e_U + e_UL + e_TR) / 4

if e_i ≤ average:  w_i = min(w_i + 1, 64)   (neighbor rewarded)
else:           w_i = max(w_i − 1, 0)    (neighbor penalized)
```

With uniform weights (`8` each) the filter reduces to simple average of 4 neighbors; as one neighbor dominates locally, prediction tends toward it. Since the state evolves deterministically from already-reconstructed (causal) values, the decoder reproduces exactly the same prediction — **zero extra bit cost**.

**2nd Order Formula** (first filter to use neighbors beyond `L`, `U`, `UL` — extends horizontal and vertical temporal context):

In addition to the three neighbors already used by other filters, 2nd Order also uses:
- `LL`: byte two positions left, same line (`x − 2×bpp`)
- `UU`: byte same column, two lines above (`x` in line `y − 2`)

```
pred_h = 2×L − LL   (linear extrapolation of horizontal trend)
pred_v = 2×U − UU   (linear extrapolation of vertical trend)
prediction = clamp((pred_h + pred_v) / 2, 0, 255)
```

Unlike other filters — which only combine or choose between existing neighbors (thus naturally limited to `[0, 255]`) — linear extrapolation can mathematically produce values outside this range (e.g., increasing sequence `LL=0, L=255` extrapolates to `510`). Therefore 2nd Order applies explicit `clamp` to the result before converting to `u8`, rather than wraparound. This **does not compromise reversibility**: the residual is still calculated as `original_byte − prediction` (with modulo 256 wraparound, next section) and reversed as `residual + prediction` — since the prediction function is deterministic and uses only already-known/causal neighbors in both encoding and decoding, it produces exactly the same value on both sides, regardless of using clamp or wraparound internally.

Genuinely distinct from Average (filter `3`): Average predicts the static average of `L` and `U`; 2nd Order predicts the **continuation of local trend**, favoring regions with smooth and consistent gradients (ramps, continuous shading) over flat regions.

All filters calculate the final residual (`original_byte − prediction`) and reverse it (`residual + prediction`) using integer arithmetic with modulo 256 wraparound (`u8` wrapping), consistent between encoding and decoding — this applies even to 2nd Order, whose internal clamp affects only the prediction calculation itself, not the residual step.

**Each filtered block (tile) is prefixed by 1 byte** indicating which code was used (a single code for all lines of the block). The decoder only reverses the operation indicated by that byte — **the heuristic used by the encoder to choose the filter is not part of the decoding contract** and can vary between implementations without affecting interoperability. Known heuristics, in order of increasing computational cost and result quality:

| Heuristic | Cost | Remark |
|---|---|---|
| Sum of absolute values of residuals (MSAD) | Low | Classic PNG heuristic; assumes small residual compresses well, which is not always true |
| Shannon Entropy (order zero) of residuals | Low/medium | Captures pattern repetition, more aligned with what ZSTD entropy stage exploits; recommended as default |
| Real compression test (compress each candidate and compare final size) | High | Optimal result, but expensive — appropriate for optional maximum compression mode, not standard use |
| QuickPrune (v1.1) | Low/medium | Fast MSAD followed by Shannon Entropy on top 8 candidates; ~1-2% compression gain with modest overhead |
| AdaptiveEntropy (v1.1) | Medium | Block type analysis (Smooth/Natural/HighFreq/Mixed) + content-aware filter selection; ~2-3% gain on natural photos |

An encoder is free to implement any of these (or another) without breaking compatibility with any CAFE decoder, as long as it correctly writes the code of the filter actually used in each block.

**Bytes per pixel (bpp)**, used to locate the "left neighbor": `bpp = bytes_per_sample × channels`, where `bytes_per_sample` is `1` for `bit depth ≤ 8` (including `1, 2, 4` packed — in that case the "channel" is already the packed byte, sections 4.1.1/4.1.2), `2` for `bit depth = 10, 12, 16` (16-bit container, section 4.1.3), and `4` for `bit depth = 32`. Minimum `bpp = 1`.

**Tile edges:** since each `IDAT` is independent (streaming), the "above" neighbor only exists if the line **is not the first of the tile** — in the first line of each tile, the filter treats the above neighbor as all-zero, same convention as PNG for the first line of the entire image. This slightly reduces efficiency at small tile edges, but preserves the independence required by streaming (section 6). The same principle applies to extended neighbors of 2nd Order filter (`8`): `LL` is treated as zero when fewer than two columns are available left (`x < 2×bpp`), and `UU` is treated as zero when fewer than two lines are available above within the tile (first **or** second line of tile). Top-right neighbors of filters `14` and `15` follow the same convention: `TR` is treated as zero at the tile right edge (`x + bpp ≥ bytes_per_line`) or in the first line. The adaptive state of Weighted filter (`15`) is reset at the start of each block/tile and shared across all lines of the block — the decoder derives the same state in the same scan order.

#### 4.3.2 Byte-shuffle (`Filter method = 1`) — implemented in reference since v1.1

Reduces entropy of **multi-byte sample** data before compression, reordering bytes by position within the sample. It is a preprocessing technique (not compression), like the predictive filter from section 4.3.1, and works together with ZSTD from section 3.2.

**When to use:** designed primarily for `Sample format = 1` (float) or `2` (half-float) and high `bit depth`, where natural interleaved order (byte 0 of R channel, byte 0 of G channel, ...) mixes bytes of different significance in the same compressed block. By grouping all bytes of the same position (e.g., all least significant bytes of all pixels, then most significant), correlation between adjacent bytes increases and ZSTD compresses better.

**Transformation (lossless, bijective):** for a block/tile with `P = width × height` pixels and `bpp` bytes per pixel, the natural buffer is

```
[byte0_p0, byte1_p0, …, byte(bpp−1)_p0, byte0_p1, …, byte(bpp−1)_p(P−1)]
```

and the shuffled buffer groups by byte position:

```
[byte0_p0, byte0_p1, …, byte0_p(P−1), byte1_p0, byte1_p1, …, byte(bpp−1)_p(P−1)]
```

**Constraints (encoder and decoder must validate):**

- `bpp ∈ {2, 4, 8, 16}`. Outside this set, `Filter method = 1` is invalid — encoder must refuse to write and decoder must reject the file (or treat as format error). This excludes `Color type = 3` (indexed, `bpp = 1`) and `bit depth < 8` (sub-byte samples have no bytes to reorder). In particular, `bpp = 1`, `3`, `6`, `12` are not supported.
- **No filter byte prefix**: unlike the predictive filter (which prefixes 1 byte per block), byte-shuffle **adds no** header byte — the `IDAT` payload is exactly the shuffled buffer.
- **Incompatible with interlace** (`Interlace method ≠ 0`): interlace requires 8-bit uint RGBA (`bpp = 4`), and the pass pipeline does not combine with reordering — encoder must reject the combination.
- **Applied per block/tile**: each `IDAT` is shuffled (and unshuffled) independently, with that tile's dimensions (`tile width × tile height`, not entire image) — preserves streaming independence from section 6. Decoder derives tile height from decompressed payload size (`tiles_in_block = payload_len / bytes_per_line`), and tile dimensions come from `iDIM` in case of 2D tiling.
- **Pipeline order**: byte-shuffle is applied **before** compression fallback (section 3.2) and after any sample packing; it is not combined with predictive filter (they are mutually exclusive — only one `Filter method` is written in `IHDR`).

**Decoding:** reversing the transformation is the bijective inverse operation, lossless. Decoder validates `bpp`, dimensions, and buffer size before unshuffling (same checks as section 12.1), and unshuffles before any predictive filter — in practice, before color conversion (section 4.1.3) and, for HDR, before tone mapping (section 7).

### 4.4 `cHDR` (ancillary, optional — HDR metadata — **implemented in reference since v1.0**)

> **Status:** HDR metadata supported in reference implementation since v1.0 (encode via `EncodeOptions.chdr_metadata` / flags `--chdr-*` in CLI; decode exposes `DecodeResult.chdr_metadata`). Malformed `cHDR` chunks are silently discarded, per section 12.4.

| Field | Size | Description |
|---|---|---|
| Transfer function | 1 byte | `0`=linear, `1`=PQ (SMPTE 2084), `2`=HLG, `3`=sRGB/gamma |
| Color primaries | 1 byte | `0`=sRGB/BT.709, `1`=BT.2020, `2`=DCI-P3 |
| Max luminance | 4 bytes float | In nits |
| Min luminance | 4 bytes float | In nits |
| MaxCLL | 4 bytes (optional) | Maximum Content Light Level |
| MaxFALL | 4 bytes (optional) | Maximum Frame Average Light Level |

**Optional field presence:** the decoder determines whether `MaxCLL` and/or `MaxFALL` are present from the chunk's `Length` field (section 3): `Length = 10` → mandatory fields only; `Length = 14` → mandatory + `MaxCLL`; `Length = 18` → mandatory + `MaxCLL` + `MaxFALL`. Including `MaxFALL` without `MaxCLL` is not permitted (fixed order); a `Length` matching none of these three combinations is invalid and the chunk must be rejected (but since it is ancillary, this does not invalidate the entire file).

**Default color space (in absence of `cHDR`):** in the absence of `cHDR` chunk (and `iCCP` chunk, section 4.7), all CAFE RGB values must be interpreted as **sRGB (IEC 61966-2-1)**. This removes any ambiguity about how to display colors in a file that carries no explicit color metadata — the default behavior is well-defined, not "undefined" or "decoder-dependent", exactly as PNG assumes sRGB in the absence of `gAMA`/`cHRM`/`iCCP`. A decoder not implementing `cHDR`/`iCCP` is therefore always correct treating colors as sRGB.

### 4.5 `eXIF` (ancillary, optional, single instance — EXIF metadata)

Stores EXIF metadata (camera, capture date, geolocation, orientation, etc.) using the standard already defined by CIPA's Exif specification — same approach adopted by PNG since 2017 (chunk `eXIf`).

| Field | Size | Description |
|---|---|---|
| Payload | rest of `Data` | Raw EXIF blob, in complete TIFF format (including its own byte order header, `II*\0` or `MM\0*`), exactly as defined by Exif specification |

- CAFE **does not interpret or transform** the content — it is stored as an opaque blob, byte-for-byte, as the Exif specification defines.
- **Compression**: follows standard fallback rule (section 3.2).
- **Single instance per file**: a decoder finding more than one instance must consider only the first and ignore others.
- **Recommended position**: before first `IDAT`.
- **Ancillary**: a decoder not interpreting EXIF simply ignores the chunk and continues reading the image normally — no pixel information depends on it.

### 4.6 `jSON` (ancillary, optional, multiple instances allowed — application JSON metadata)

Stores arbitrary metadata defined by applications or users in JSON format, when the data does not fit any standardized chunk (e.g., `eXIF`) — such as edit history, catalog tags, provenance, accessibility alt-text, or pipeline data from a specific tool.

**Payload (before compression):**

| Field | Size | Description |
|---|---|---|
| Namespace length | 1 byte | Size of Namespace field |
| Namespace | N bytes | ASCII string (e.g., `"app.editor"`, `"catalog.tags"`, `"user"`) |
| JSON payload | rest of `Data` | Valid UTF-8 text, free structure |

- **Namespace** prevents collision between metadata from different sources (tools, plugins, end user). Limited to 255 bytes.
- **Multiple `jSON` instances** are allowed in the same file, each with its own namespace. Decoders must filter by namespace they recognize and ignore others.
- **Compression**: follows standard fallback rule (section 3.2) — JSON tends to compress well with ZSTD.
- **Recommended position**: after `eXIF` (if present) and before first `IDAT`.
- **Validation**: a malformed `jSON` (namespace length inconsistent, or invalid JSON) **must not invalidate the file or cause fatal decoding error**, being ancillary — decoder discards only that specific chunk and continues (see section 12.4).
- **Usage recommendation**: keep payload small (few KB). For large user-defined binary blobs, prefer a dedicated binary chunk instead of JSON.

#### 4.6.1 Convention for plain-text comments

CAFE **does not define a dedicated chunk for free-form text comments** (an earlier version of this spec proposed a separate `cOMM` chunk, but it was dropped for entirely overlapping `jSON`). Instead, the recommended convention is to use the **`"comment"`** namespace within a `jSON` chunk:

```json
{"text": "Created with CAFE Encoder v1.0", "author": "optional"}
```

This avoids having two competing free-text metadata mechanisms in the format, keeping `jSON` as the single entry point for non-standardized application metadata.

### 4.7 `iCCP` (ancillary, optional, single instance — ICC color profile)

Stores an ICC (International Color Consortium) color management profile, for workflows requiring color reproduction accuracy beyond standard sRGB.

| Field | Size | Description |
|---|---|---|
| Payload | rest of `Data` | Raw ICC profile (binary), format defined by ICC specification |

- CAFE **does not interpret** the profile content — it is stored as an opaque blob.
- **Compression**: follows standard fallback rule (section 3.2).
- **Single instance per file.**
- **Interaction with `cHDR`**: if both chunks are absent, the default sRGB rule from section 4.4 applies. If `iCCP` is present, it takes precedence over sRGB assumption.
- **Recommended position**: before first `IDAT`.

### 4.8 `xMPd` (ancillary, optional, single instance — XMP metadata)

Stores metadata in XMP format (Extensible Metadata Platform, Adobe/ISO 16684-1 standard) — useful for compatibility with editorial and digital asset management pipelines already using XMP in other formats (JPEG, TIFF, PNG).

| Field | Size | Description |
|---|---|---|
| Payload | rest of `Data` | Valid UTF-8 XML, per XMP specification |

- **Compression**: follows standard fallback rule (section 3.2) — XML tends to compress well.
- **Single instance per file.**
- **Recommended position**: before first `IDAT`.
- **Overlap with `jSON`/`eXIF`**: applications are expected to choose **one** metadata mechanism per data type (EXIF for capture data, XMP for editorial flow, JSON for application-proprietary data) — CAFE does not mandate which, only provides all three.

### 4.9 `zDIC` (ancillary, optional, single instance — ZSTD dictionary)

Stores a ZSTD dictionary used to **improve compression of `IDAT` chunks** — especially valuable in small images or with repetitive patterns that benefit from a pre-trained dictionary (e.g., `zstd::dict::from_samples`), since small blocks individually do not give ZSTD enough context to compress well alone.

| Field | Size | Description |
|---|---|---|
| Payload | rest of `Data` | Raw ZSTD dictionary (format defined by ZSTD library — may be a formally trained dictionary with embedded `Dictionary_ID`, or a "raw content dictionary" without such formality) |

- **Scope**: the dictionary applies **only to `IDAT` chunks** of the file — not to `eXIF`, `jSON`, `iCCP`, or `xMPd`, which continue using ZSTD without dictionary. This scope restriction simplifies implementation and keeps metadata decodable regardless of `zDIC` presence/absence.
- **Real use in compression (functional, not decorative)**: when present, **all** `IDAT` chunks with `Flag = 0x01` (ZSTD) in the file were compressed using this dictionary — mixing `IDAT` with and without dictionary in the same file is not permitted. Decoder must provide the same dictionary to decompressor when processing any `IDAT`.
- **Mandatory position**: before first `IDAT` (decoder needs dictionary available before processing any chunk depending on it).
- **Behavior with formally trained dictionary**: if the dictionary was generated with a formal training tool (contains `Dictionary_ID`), decompression **fails explicitly** (`Dictionary mismatch`) if decoder tries a different dictionary or none — this is a property of ZSTD format itself, not something CAFE needs to implement separately.
- **Single instance per file.**

### 4.10 `IEND` (critical, marks end of file)

`Length = 0`. No `Data`.

## 5. Interlacing

- `Interlace = 1` (Adam7): 7 progressive passes, same logic as PNG, adapted to produce one `IDAT` per (tile, pass) combination.
- `Interlace = 2` (even/odd): 2 passes, lower implementation complexity, simpler UX benefit.
- `Interlace = 0`: no interlacing, linear top-to-bottom decoding.

Each `IDAT` includes `pass_number` at the start of the payload (before compression) when interlace ≠ 0. Interlacing applies to both the direct RGBA path and the indexed palette path (in the latter case, via intermediate RGBA conversion — see section 4.3).

### 5.1 Design decision: why there is no fourth interlacing mode

The spec intentionally **does not** add `Interlace = 3` (or any other scheme beyond the three above), even though plausible variations exist (e.g., pyramid/mipmap-style scheme with resolution doubling per pass).

Reason: `Interlace method` is an `IHDR` field — therefore **critical**, not ancillary. A decoder not recognizing the value cannot decode the image at all; it is not a feature that degrades gracefully, it is an unreadable file for that decoder. This is fundamentally different from adding a new chunk (like `iCCP` or `xMPd`), which an outdated decoder can safely ignore and still read the image.

Each new interlacing mode is, in practice, an implementation obligation for **every** decoder claiming CAFE compatibility — conformance complexity grows combinatorially (against bit depth, color type, predictive filter, palette), not linearly.

The three existing values already cover real use cases:

| Need | Already solved by |
|---|---|
| Blurry preview of entire image, refining by resolution | `Interlace = 1` (Adam7) |
| Simple refinement, lower implementation overhead | `Interlace = 2` (even/odd) |
| Progressive preview by spatial region (not resolution) | `iDIM` with `scan_order = 1` (Z-order) — already ancillary, no risk of fragmentation |

If in future a real need arises for different spatial preview, the recommended path is to extend `scan_order` in `iDIM` chunk (ancillary), not add a new `Interlace method` (critical).

## 6. Streaming

Requirements for incremental decoding:

1. `IHDR` is always first chunk, small and uncompressed — dimensions and format become available immediately.
2. `iDIM`, if present, informs the tile scheme before any `IDAT`, allowing client to set up a full-image placeholder.
3. Each `IDAT` is self-contained and can be decoded as soon as it arrives, without waiting for others — except when `zDIC` is present, in which case the dictionary (read before first `IDAT`) must be available when processing any subsequent `IDAT`.
4. Combining `scan_order = 1` (Z-order) with `Interlace = 1` is recommended for best progressive loading experience (low-quality preview of entire image, refining over time).

## 7. HDR Extensibility (implemented in reference since v1.0)

Full HDR flow support in reference implementation, at format level:

- `Sample format` in `IHDR` (uint / float / half-float) — encode via `EncodeOptions.sample_format` / `--sample-format`; decode converts float/half back to RGBA (section 4.1)
- `cHDR` chunk as ancillary (section 4.4) — implemented since v1.0; old decoders ignore and continue working
- `iCCP` chunk (section 4.7), also implemented, covers part of color management

A decoder without HDR support encountering `cHDR` should ignore it (ancillary chunk) and, if `Sample format` or `Bit depth` are incompatible with its support, must explicitly reject the file — should not attempt to interpret float data as integer. In this case, and in any file without `cHDR`/`iCCP`, the default color space rule from section 4.4 applies: colors must be interpreted as sRGB.

**Tone mapping (implemented in reference decode since v1.1, outside binary contract):** when decoder encounters `Sample format = 1` (float) **and** `cHDR` chunk, the final conversion to 8-bit RGBA applies an SDR display pipeline: (1) EOTF — `transfer_function` from `cHDR` (`0`=linear, `1`=PQ, `2`=HLG, `3`=sRGB) converts encoded values to linear luminance; (2) color primaries conversion via CIE 1931 XYZ between `cHDR` source space (`0`=BT.709/sRGB, `1`=BT.2020, `2`=DCI-P3) and destination space; (3) global tone mapping operator (ACES filmic curve in reference, Reinhard available) that compresses dynamic range to [0, 1]; (4) sRGB companding. Non-finite values (NaN/Inf), degenerate `max_luminance`, and invalid primaries/transfer are handled defensively (clamp/handleable error) — never generate panic. This pipeline is a **decoder display preference**, not part of binary contract: a decoder may ignore it and only reduce float→8-bit, and result may differ visually without breaking interoperability. **Future work:** encode SDR→HDR (inverse tone mapping), operator selection via CLI, and look-up tables.

## 8. IHDR Field Summary (quick reference)

| Byte # | Field | Values |
|---|---|---|
| 0-3 | Width | uint32 BE |
| 4-7 | Height | uint32 BE |
| 8 | Bit depth | 1, 2, 4, 8, 10, 12, 16, 32 — sub-byte (1, 2, 4) valid only with Color types `0`, `3`, and `4`; Color types `2` and `6` accept only `8, 10, 12, 16, 32` (see sections 4.1.1 and 4.1.2) |
| 9 | Sample format | 0=uint, 1=float, 2=half-float |

## 10. Design Considerations

- **Fallback per chunk** (not per file) avoids compression overhead on high-entropy blocks (noise, already-lossy-compressed data).
- **CRC per chunk** detects corruption without decompressing entire file.
- **Critical/ancillary convention** allows adding new chunks (e.g., `iCCP`, `xMPd`, future geometric annotation chunk) without breaking old decoders.
- Tile size is a trade-off: smaller tiles = more granular streaming, but more header/CRC overhead per chunk **and** lower predictive filter efficiency (section 4.3.1), since each tile restarts prediction on first line.
- **Predictive filter must not be confused with compression**: it reduces data entropy before ZSTD acts, but does not replace compression step nor fallback rule from section 3.2 — both techniques work together.

## 12. Security Considerations

A CAFE decoder processes **untrusted** source data by definition (third-party files, downloads, user uploads). This section documents the minimum requirements any implementation must follow to not expose the host application to denial-of-service (DoS) or worse.

### 12.1 General principle: decoders must never panic/crash on untrusted input

Every size, count, or offset field read from a `.cafe` file is, by definition, controlled by whoever created the file — including an attacker. A correct decoder **validates these fields before using them** to index memory, allocate buffers, or divide values, and returns a handleable error (not an uncaught exception/panic/segfault) for any malformed input. This includes:

- Truncated files (smaller than expected at any parsing point).
- Forged `Length` fields (larger than actually available data, or large enough to cause arithmetic overflow when summed with offsets).
- Critical chunks (`IHDR`, `PLTE`, `IDAT`) with size smaller than spec-required minimum.
- Degenerate dimensions (`Width = 0` or `Height = 0`), which must not be used to divide any other value without prior checking.
- Inconsistency between dimensions declared in `IHDR` and actual pixel data reconstructed from `IDAT` — must generate explicit error, not attempt to build image with wrong buffer size.

### 12.2 Protection against "decompression bomb" (CWE-409)

Like any format employing generic compression, CAFE is vulnerable to the same "zip bomb" attack principle: a compressed chunk of a few KB can, in theory, expand to gigabytes when decompressed, exhausting all available process memory before any content validation occurs.

**Mandatory requirement**: every decoder must impose a **configurable upper limit** on output size of any decompression operation (per chunk), rejecting decompression as soon as this limit is exceeded — without ever attempting to allocate or materialize full content beyond the limit before checking. Reference implementation uses **1 GiB per chunk** as default value, generous enough for realistic highest-resolution images, but finite.

This is independent of (and complementary to) any size limit on the `.cafe` file itself — the objective here is specifically about the **decompression expansion ratio**, which can be arbitrarily high even in small files.

### 12.3 Absence of upper limit for `Width`/`Height`

The spec defines no maximum limit for `Width`/`Height` in `IHDR`. This is intentional (avoids imposing an arbitrary ceiling that could invalidate legitimate use cases), but implies decoders must treat these values as untrusted for pre-allocation purposes: image reconstruction must occur incrementally, from actual pixel data received in `IDAT` (respecting per-chunk limit from section 12.2), not via single `Width × Height × bytes_per_pixel` allocation made **before** any real data has been validated.

### 12.4 Malformed ancillary chunks never invalidate file or generate panic

Reinforcing convention from section 3.1: an ancillary chunk (`eXIF`, `jSON`, `iCCP`, `xMPd`, `zDIC`, `cHDR`) with malformed content — inconsistent namespace, invalid JSON, invalid XML, invalid UTF-8 — must be **silently discarded** by decoder (or reported as non-fatal warning), must never interrupt image decoding itself, and must never cause panic. The only exception is when the chunk is structurally impossible to delimit (e.g., `Length` exceeding file) — in that case, the error is framing (section 12.1), not content, and is handled at chunk parser level, not at that chunk's specific parser.

### 12.5 Scope of this audit

The guidelines above reflect a security audit of reference implementation in Rust, covering: chunk reading (framing), `IHDR` header, decompression (with and without `zDIC` dictionary), indexed palette decoding, `jSON` chunk, final image assembly, **byte-shuffle** (section 4.3.2), and **HDR tone mapping** (section 7). All points were validated with adversarial tests (truncated files, forged fields, degenerate dimensions, real decompression bomb of ~1 GiB disguised in tens of KB, NaN/Inf values, degenerate `max_luminance`/`bytes per pixel`) confirming handleable error behavior, no panic, in all cases.

Specific audit requirements for v1.1 additions:

- **Byte-shuffle**: strict validation of `bpp ∈ {2, 4, 8, 16}` before any indexing; overflow-protection on `width × height × bpp`; exact buffer size check (truncation → handleable error, never read out-of-bounds); defensive tile height derivation (`len / bytes_per_line` with `bytes_per_line` guarded against zero).
- **Tone mapping**: division by zero avoided (EOTF with protected denominator; `max_luminance.max(1.0)`); NaN/Inf in channels handled explicitly via `is_finite()`; overflow on `width × height × 16` via `checked_mul`; exact float buffer size validation; values outside [0, max] clamped before operator.
